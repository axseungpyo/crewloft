# Agent Office — 상시 조직과 프로젝트 TF

> 2026-10-01 통합 메모: R0는 주간 콘텐츠 프로젝트 1개로 검증하며 여러 TF 동시 운영은 R0 제외(결정 36). 이 문서의 TF 구조는 제품 범위로 유지한다.
> 2026-10-02 갱신: 상시 4인 기본값은 폐기(결정 54). 첫 직원은 사업 파트너 매니저이고 이후 한 명씩 채용한다. 승급은 실적 기반 제안 + 사용자 결정이며 책임 범위를 넓힌다(결정 57, 예: 실장이 되면 새 프로젝트 TF 제안 가능). 외부 게시·발송·결제·고용 확인은 직급과 무관하게 유지한다.

상태: 상시 핵심 직책을 유지하고 프로젝트마다 전문가를 고용해 TF를 구성하는 방향은 사용자 확정. 아래 세부 운영/화면 규칙은 기획 제안이다.

## 사용자 결정
일반 회사처럼 운영한다. 메인 직책은 사무실에 유지하고, 프로젝트를 시작하면 TF Team을 구성하듯 필요한 전문가를 고용한다.

## 조직 구조
- **사무실/회사:** 조직의 목표, 상시 직원, 공통 자료, 앱/AI 연결과 운영 정책을 갖는다.
- **상시 직원:** 프로젝트 종료 후에도 소속과 기본 직책을 유지한다. 초기 직책은 사업 설명을 바탕으로 AI가 제안하고 사용자가 수정·고용한다. 총괄 매니저는 기존 합의대로 전체 진행을 책임진다.
- **프로젝트 TF:** 프로젝트 목표와 완료 조건을 달성하기 위한 임시 팀. 참여하는 상시 직원과 새로 고용하는 전문가를 포함한다.
- **TF 전문가:** 부족한 역량을 보완하기 위해 프로젝트별로 고용하는 직원. 채용 이유와 구체적인 업무를 제시하고 사용자 확인 후 고용한다.

회사 규모를 흉내 내기 위해 불필요한 임원/직책을 늘리지 않는다. 상시 직책의 구체적인 목록과 인원은 아직 정하지 않았다.

## 직원과 배치의 구분 — 제안
직원 자체와 프로젝트 참여를 별도로 관리한다.
- 직원: 이름, 기본 직책, 역량, 사용자 선호, 허용된 도구/AI 연결.
- 프로젝트 배치: TF 내 역할, 담당 업무, 우선순위, 프로젝트 자료 접근 범위, 참여 기간.
- 같은 상시 직원이 다른 프로젝트에 참여해도 별개의 복제 직원으로 만들지 않는다.
- TF 내 역할은 기본 직책과 다를 수 있다. 예를 들어 상시 리서처가 특정 TF에서는 고객조사 담당을 맡는다.
- 여러 TF의 업무량이 충돌하면 매니저가 사용자 우선순위·마감·허용 범위 안에서 배치와 업무 순서를 조정하고 영향을 보고한다. 이 원칙은 사용자가 승인했다.

## 프로젝트 시작 흐름
1. 사용자가 새 프로젝트를 설명한다.
2. 매니저가 필요한 질문으로 목표·첫 결과물·제약을 정리한다.
3. 기존 상시 직원의 역량과 가능한 참여 범위를 확인한다.
4. TF 구성안을 제시한다: 기존 직원 배치 + 필요한 전문가 채용 + 업무별 책임.
5. 사용자가 팀 구성을 수정하고, 신규 고용과 첫 업무를 확인한다.
6. TF가 프로젝트 채널/DM/업무에서 협업한다. 직원 간 직접 인계와 매니저의 전체 진행 관리 원칙은 유지한다.

첫 방문에는 같은 사업 설명으로 초기 상시 조직과 첫 TF를 함께 제안할 수 있다. 별도의 긴 회사 설립 설문을 필수로 추가하지 않는다.

## TF 제안 화면 — 제안
| 표시 | 내용 |
| --- | --- |
| 기존 직원 참여 | 이름, 기본 직책, 이번 TF 역할, 현재 맡은 업무 |
| 전문가 채용 | 전문 분야, 필요한 이유, 첫 업무, 사용하는 AI/도구 |
| 책임자 | 누가 진행을 정리하고 결과를 종합하는지 |
| 업무 흐름 | 자료를 누가 만들고 누구에게 전달하는지 |

직원 카드에는 `상시 직원` / `TF 전문가`를 구분하고, 여러 프로젝트에 참여 중이면 참여 프로젝트를 표시한다. 고용되지 않은 전문가를 이미 일하고 있는 직원처럼 표현하지 않는다.

## 프로젝트 종료 — 미확정 상세 제안
- 결과 확인 후 TF 활동을 종료하고 프로젝트 기록을 보관한다.
- 상시 직원은 사무실에 남고 해당 프로젝트 배치만 종료한다.
- TF 전문가는 작업을 멈춘 대기 인재로 보관하는 방안을 제안한다. 이후 재고용 또는 상시 직원 전환을 선택할 수 있다.
- 기록 보관과 에이전트의 계속 실행은 다르다. 종료된 TF가 백그라운드에서 계속 업무나 AI 호출을 수행하지 않도록 한다.
- 상시 전환/재고용은 사용자가 확인한다. 자동 채용 정책을 새로 부여하지 않는다.
- 종료 시 전문가 기록을 어떻게 재사용하고 언제 삭제하는지는 기억/보존 정책과 함께 확정한다.

## 지식과 권한 — 기본 원칙 합의
- 회사 공통 지식: 사업 소개, 브랜드 원칙, 사용자 업무 선호 등.
- 프로젝트 지식: 목표, 조사 자료, 의사결정, 결과물 등.
- 직원 경험: 업무 방식에 대한 피드백, 재사용 가능한 역량과 선호.

사용자는 공통 원칙과 검토된 교훈을 회사에 공유하고, 원본 자료·대화를 프로젝트별로 관리하는 방향을 승인했다. 상시 직원이라는 이유만으로 모든 프로젝트 자료에 자동 접근하거나, 다른 고객/프로젝트의 정보를 섞지 않는다. 승격 검토 절차와 상세 공유 범위 제안은 `knowledge.md`를 참조한다.

## 기존 합의와의 연결
- AI가 채용 이유와 팀 구성을 제안하고 사용자가 수정 후 고용한다.
- 매니저는 전체 진행을 책임지고, 직원들은 직접 DM으로 협업한다.
- 외부 게시/발송/결제/추가 고용은 사용자 확인을 받는다.
- Notion, Google Drive·Docs, Slack은 설정에서 연결한다.
- A 기반2D 사무실에서 상시 소속과 TF 참여를 이해할 수 있게 표현한다. 물리적인 방/층/좌석 배치 방식은 아직 확정하지 않았다.

## 여러 TF의 조정 — 사용자 합의
- 동일한 상시 직원을 여러 TF에 배치할 수 있다. 무제한 동시 실행을 의미하지는 않는다.
- 매니저는 사용자가 정한 프로젝트 우선순위와 마감, 허용 범위 안에서 업무 순서/배치를 조정한다.
- 사용자에게 무엇이 바뀌고 어떤 일정/결과물에 영향을 주는지 보고한다.
- 추가 인력이 필요하면 채용 이유와 영향을 제안하고 사용자 확인을 받는다.
- 기존 목표/마감/예산을 만족할 수 없으면 선택이 필요한 변경안을 제시한다. 자동 배치 권한으로 목표나 한도를 임의 변경하지 않는다.
- 구체적인 작업 선점/재개 방식, 동시 실행 수, 우선순위 동률 해소 규칙은 후속 상세 설계 대상이다.
