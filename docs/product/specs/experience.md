# Agent Office — 첫 버전 사용자 경험 제안

> 2026-10-01 통합 메모: 화풍은 A 기반 2D로 확정(결정 14·15). 비용은 구독 한도 기반(결정 23), 실행 환경은 R0→R1→R2 순서(결정 24). 현재 합의 상태는 [PRD](../PRD.md)를 기준으로 한다.

상태: 2026-09-27 사용자가 화면 구성과 사용자 경험 방향을 승인함. 후속으로 Notion, Google Drive·Docs, Slack을 모두 첫 버전 연동 대상으로 선택함. 명시된 미결정 사항은 별도 결정이 필요하다. 구현 착수 전 기획 문서이다.
기준 문서: `../PRD.md`
목표: 사업 설명에서 첫 팀의 실제 결과물까지 이어지는 경험을 구체화한다.

## 1. 제품의 약속
“하고 싶은 사업을 설명하면, 필요한 AI 직원을 제안받고 함께 일하는 사무실을 운영할 수 있다.”

일반 사용자가 알아야 할 것은 목표, 맡길 일, 결과, 필요한 결정이다. 실행에 필요한 모델/도구 설정은 별도 설정 영역에서 다루되, 연결되지 않은 앱이나 없는 능력을 이미 사용할 수 있는 것처럼 제안하지 않는다.

## 2. 화면 구성 대안
| 대안 | 장점 | 주요 한계 |
| --- | --- | --- |
| 사무실 중심 + 업무 상세 패널 (추천) | 직원이라는 개념과 실제 진행을 함께 이해하고, 직원에서 대화/업무로 바로 이동 | 작은 화면과 직원 수 증가에 대응할 목록 보기가 필요 |
| 업무 보드 중심 + 작은 사무실 | 많은 업무를 비교하고 관리하기 쉬움 | 사무실 경험이 부가 요소로 밀릴 수 있음 |
| 매니저 채팅 중심 + 필요 시 사무실 | 설명하고 지시하는 시작이 단순함 | 직원별 상태와 동시 진행을 한눈에 파악하기 어려움 |

추천안은 사무실을 기본 화면으로 두고, 대화·업무·결과물을 같은 화면의 상세 패널에서 확인하게 한다. 목록/보드 보기는 업무가 많아졌을 때 선택하는 보조 보기다. 화풍은 A 기반 2D 일러스트로 확정했다(결정 14·15).

## 3. 첫 방문부터 첫 업무까지

### 사업 설명
- 주요 입력: “어떤 사업이나 프로젝트를 맡기고 싶나요?”
- 텍스트 설명으로 시작하고 자료/링크는 선택적으로 추가한다.
- 기존 사업과 새 사업을 모두 설명할 수 있다.
- 초기 안내는 고용 전의 서비스 안내다. 이 단계에서 임의로 유료 직원이나 팀을 실행하지 않는다.
- 설명 다음에 AI를 연결한다. 면접부터 AI가 일하므로 연결 전에는 면접을 시작하지 않는다.

### 첫 채용 — 매니저 면접 (결정 54·55)
- 첫 직원은 사업을 가장 잘 이해하고 기획·전략을 함께 세울 매니저다. 나중에 승급할 수 있다(결정 57).
- 면접은 미니 사업 회의다. 후보 2–3명이 사업 설명을 읽고 각자 방향, 첫 한 달 계획, 먼저 묻고 싶은 것을 제시한다. 생성에 쓴 추정 사용량을 표시한다.
- 후보는 모두 같은 AI 연결을 쓴다. 차이는 일하는 방식 설정이며 나중에 바꿀 수 있다고 알린다.
- 고른 후보는 외형·이름, 말투(나에게 말할 때: 해요/합니다/반말, 이모지), 성향 슬라이더(신중↔과감, 꼼꼼↔빠름, 직관↔데이터, 질문 먼저↔제안 먼저), 보고 스타일(길이, 빈도, 확인 질문 정도)로 조절한다. 바꾸는 즉시 "이렇게 말해요" 예시 문장이 바뀐다.
- 성향은 능력치가 아니다. 숙련도·능력치는 실제 기록으로만 자란다. 결과물 문체는 직원 말투가 아닌 브랜드 톤을 따른다. 확인 질문을 적게 해도 외부 게시·발송·결제·추가 고용은 항상 확인한다.
- 계약서(직위, 맡는 일, 일하는 방식, AI, 항상 지키는 것, 승급 경로)에 도장을 찍으면 고용되고 사무실에 자리가 생긴다.

### 필요한 내용 구체화 — 매니저와 사업 기획 회의
- 고용한 매니저가 정한 말투로 진행한다. 면접에서 제안한 방향이 출발점이다.
- 목표와 첫 결과물, 대상, 제약 중 다음 행동에 영향을 주는 정보만 확인한다.
- 이미 답한 질문은 반복하지 않는다.
- 선택지와 자유 입력을 제공한다. 사용자가 모르는 질문에는 “조사해서 제안받기” 경로를 제공한다.
- 확정 사실, 사용자 선호, 아직 검증하지 않은 가정을 구분한다.
- 첫 업무를 정의할 수 있으면 브리프와 채용 로드맵으로 넘어간다. 완성된 사업계획서를 요구하지 않는다.

### 채용 로드맵과 다음 채용 (결정 56)
매니저가 한 명씩 채용을 제안한다. 한 화면에서 다음을 검토할 수 있게 한다.
- 이번 프로젝트의 목표와 첫 결과물.
- 로드맵: 역할, 채용 이유, 시점(지금 / N주 차 / 필요할 때), 협업 관계.
- 지금 뽑을 역할의 후보 2명과 내 주제로 만든 짧은 샘플(추정 사용량 표시). 고른 뒤 매니저와 같은 방식으로 조절해 고용한다.
- 업무에 필요한 앱 연결과 권한의 준비 여부.
- 비용 제한과 기본 확인 정책. 실제 예산 금액/모델 요금 정책은 후속 결정이다.

“작가는 지금 뽑자”처럼 자연어로 로드맵을 바꿀 수 있다. 인원에 따라 지금 할 수 있는 일과 다음 채용 후 가능한 일을 갱신한다. 고용은 매번 사용자의 명시적인 행동(계약서 도장)으로만 일어난다. 앱 연결이 없어도 가능한 준비 업무와 연결이 필요한 후속 업무를 구분한다.

## 4. 사무실 화면
| 영역 | 내용 | 주요 행동 |
| --- | --- | --- |
| 상단 | 현재 프로젝트, 목표, 진행 중/결정 대기 요약, 실행 장소와 연결 상태 | 프로젝트 맥락 확인, 전체 일시정지 |
| 중앙 | 직원, 책상/공용 협업 공간, 실제 상태에 대응하는 모션 | 직원 선택, 진행 중 인계 확인 |
| 상세 패널 | 선택한 직원의 현재 업무, 사용자 DM, 관련 동료 대화, 결과물 | 직접 지시, 관련 업무 열기 |
| 활동 기록 | 시작·인계·수정·완료 등 중요한 변화 | 사건에서 업무/대화/결과물로 이동 |
| 결정 및 결과함 | 사용자 판단이 필요한 항목, 전달받은 결과 | 검토, 수정 요청, 실행 확인, 보류 |
| 설정 → 연결된 앱 | Notion, Google Drive·Docs, Slack의 계정·연결 상태·사용 범위 | 연결, 관리, 재연결, 해제 |

직원 선택의 첫 화면은 “지금 무엇을 하고 있고, 무엇이 필요하며, 무엇을 만들었는지”를 설명한다. 긴 실행 기록은 사용자가 펼쳐 볼 수 있게 한다.

대기 이유는 색상만으로 전달하지 않는다. 상태 문구와 아이콘을 함께 사용하고, 모션 감소 또는 목록 보기에서도 같은 정보를 확인할 수 있도록 설계한다.

## 5. 직원 간 협업
예시: 리서처가 조사 결과를 콘텐츠 담당자에게 전달한다.
1. DM에 자료와 관련 업무가 함께 표시된다.
2. 상대 직원이 인계를 수락하면 다음 업무의 담당자와 상태가 기록된다.
3. 사무실에서는 자료 전달에 대응하는 모션을 보여준다.
4. 콘텐츠 담당자는 누락 자료를 리서처에게 직접 요청할 수 있다.
5. 매니저는 목표, 우선순위, 업무 의존관계와 충돌을 관리한다. 모든 메시지를 매번 중계하지 않는다.

의사결정 규칙 제안:
- 자료 전달과 도움 요청은 직원끼리 자율적으로 한다.
- 기존 목표/허용 범위 안의 업무 조정은 기록을 남기며 수행한다.
- 충돌하거나 목표/범위를 바꾸는 조정은 매니저가 정리하고 필요 시 사용자에게 제시한다.
- 추가 고용과 외부 게시/발송/결제는 합의한 사용자 확인 정책을 따른다.
- 대화가 계속된다는 이유만으로 직원을 계속 실행하지 않는다. 수행할 업무, 요청, 예약 또는 허용된 이벤트가 있을 때 활동한다.

사용자가 직원에게 직접 변경을 요청하면 해당 업무와 프로젝트 기록에도 반영한다. 매니저가 이전 지시를 계속 기준으로 삼지 않도록 변경 사실을 공유한다.

## 6. 사용자 확인 경험
예시: “콘텐츠 담당자가 게시 준비를 마쳤습니다.”
- 무엇을: 실제 게시할 내용과 첨부물.
- 어디에: 연결 앱, 대상 계정/채널.
- 언제: 즉시 또는 예정 시점.
- 비용이 있는 경우: 확인 가능한 금액과 조건.
- 행동: 실행, 수정 요청, 보류/거절.

사용자 확인은 제시된 내용/대상/조건에 연결한다. 확인 이후 내용이나 대상이 실질적으로 달라지면 새 확인을 받는다. 초안 작성 허용을 외부 발송 허용으로 해석하지 않는다.

사용자가 부재 중이면 해당 업무와 의존 업무만 기다리고, 독립적인 다른 업무는 계속할 수 있다. 확인하지 않았다고 자동 승인하지 않는다.

## 7. 결과와 완료
- 업무 완료에는 결과물 또는 확인 가능한 실행 결과를 연결한다.
- 초안 완성과 외부 게시 완료를 별도로 표현한다.
- 외부 앱에서 결과를 확인하지 못하면 “확인 필요”로 표시한다.
- 인계 완료는 수신자의 수락으로 구분하고 단순 메시지 전송만으로 처리하지 않는다.
- 결과함에서 결과물을 열고, 수정 요청을 원래 업무에 연결한다.

## 8. 로컬/VPS와 복귀
후속 사용자 결정: 로컬, 개인 VPS 연결, 서비스 관리형 서버를 모두 제공한다. 상세는 `deployment.md`를 참조한다.
같은 사무실 경험을 서로 다른 실행 장소에서 제공하는 방향을 제안한다.
- 로컬: “이 컴퓨터에서 실행 중”으로 표시한다. 절전/종료 시 작업이 계속된다고 안내하지 않는다.
- VPS: “서버에서 실행 중”으로 표시한다. 사용자 화면을 닫아도 실행과 기록이 유지돼야 한다.
- 서버 표시는 개인 VPS와 서비스 관리형을 구분하며, 설정의 실행 환경 메뉴에서 연결 상태와 운영 주체를 확인한다.
- 접속 장애: 마지막 확인 시각과 연결 끊김을 표시한다. 확인할 수 없는 직원 상태를 실시간처럼 재생하지 않는다.
- 복귀: 새 결과, 진행 업무, 판단 요청, 실패/재연결 필요 항목을 요약한다.
- 중복 실행: 같은 사무실이 로컬과 VPS 양쪽에서 같은 일을 중복 수행하지 않게 해야 한다. 최초 버전의 실행 장소 전환/동기화 방식은 미정이다.

24시간 운영은 상시 대기와 필요한 업무 실행을 포함하는 방향으로 정의한다. 직원들이 쉬지 않고 대화하거나 모델을 호출하는 것을 목표로 하지 않는다. 예약/이벤트의 구체적인 지원 범위는 미정이다.

## 9. 단계별 구현 후보 — 아직 착수하지 않음
1. 설명 → 구체화 → 브리프 → 팀 제안/수정 흐름 검증.
2. 매니저와 직원 둘의 실제 업무 인계, 결과물, 상태 기록 검증.
3. 위 실제 상태에 연결된 사무실 모션과 상세 패널 검증.
4. Notion, Google Drive·Docs, Slack 각각의 독립 연동과 앱 간 결과 전달, 허용된 저장 및 사용자 확인 후 외부 실행 검증.
5. 화면 종료/재접속, 작업 대기/복구, 로컬/VPS 실행 검증.

단계는 개발 순서의 제안이다. 사무실 시각화, 로컬/VPS 또는 선택된 세 앱 중 일부를 제품 범위에서 제외하는 결정이 아니다. 세 앱 모두의 기본 경로와 Slack 전송 확인 경로를 검증해야 첫 버전 연동 범위가 완료된다.

## 10. 사용자 시나리오 기반 검증
| 시나리오 | 기대 결과 |
| --- | --- |
| 설명이 모호하고 사용자가 고객군을 모름 | 필요한 질문 또는 조사 제안으로 진행, 임의 확정하지 않음 |
| 제안된 직원 한 명을 제외함 | 남은 팀의 업무와 예상 결과가 조정됨 |
| 직원이 다른 직원에게 자료를 인계함 | 대화·업무·모션에서 같은 인계를 확인 가능 |
| 사용자에게 게시 확인을 요청함 | 내용과 대상이 보이며, 확인 전에는 게시되지 않음 |
| 앱 권한이 만료됨 | 관련 업무에 재연결 필요 표시, 결과가 성공으로 기록되지 않음 |
| 사용자가 작업 중 방향을 수정함 | 새 지시가 업무 및 매니저의 진행 관리에 반영됨 |
| 서버 작업 중 화면을 닫고 돌아옴 | 유지된 작업 상태와 실제 결과를 확인 가능 |
| 네트워크가 끊김 | 마지막 확인 시각 표시, 가짜 실시간 모션/완료 상태 없음 |

## 11. 미결정 사항
제품 기획을 계속 구체화할 수 있지만, 다음은 구현 전에 확정해야 한다.
- 선택된 세 앱의 상세 기능과 사용자 검증에 사용할 실제 업무.
- 기본 기기/화면 크기.
- 첫 버전 제외 후보 및 설계/구현 재량.

질문 도구 진단은 별도 터미널의 별도 작업이다. 이 문서는 그 진단을 포함하지 않는다.
