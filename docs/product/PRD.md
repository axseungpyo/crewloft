# Agent Office — 제품 요구사항 (PRD)

갱신일: 2026-10-04 · 상태: R0 MVP 구현(로컬) 후 수정 단계 — **기획 개정 중: 사업 맞춤 셋팅(결정 73, [business-setup](specs/business-setup.md))**. 아래 §1 · §2 · §5 · §11 · §12는 개정 방향을 반영했고, 구현은 P1–P4로 진행한다.
이 문서는 **현재 합의 상태의 단일 기준**이다. 근거와 변경 이력은 [결정 로그](decisions.md), 상세는 각 스펙 문서를 따른다. `(제안)` 표시는 사용자 확인 전 기획 제안이다.

## 1. 제품 정의
**혼자 또는 몇 명이 창업을 막 시작할 때, 하려는 사업을 설명하면 매니저가 사업을 이해하고 그에 맞는 AI 팀 · 업무 · 공간을 셋팅해 주는 서비스.** AI 팀이 창업 초기의 일(조사 · 계획 · 준비 · 출시 · 첫 고객)을 나눠 맡고, 대표는 확인 · 결정만 한다. 과정은 내 사업에 맞춰 생겨나는 3D 공간에서 보이고, 실제 실적으로 공간이 자란다(결정 66–68 · 73).

- 사용자는 사무실의 소유자다. 직원을 고용하고 역할을 맡기며, 필요한 결정만 내린다.
- 매니저가 전체 진행을 책임지고, 직원들은 매니저를 매번 거치지 않고 DM으로 직접 협업한다.
- 직원은 연결된 앱에 실제 결과물을 저장·게시한다. 직원별 범용 컴퓨터 조작은 하지 않는다.
- **최종 목표(결정 85): 직원 없이도 굴러가는 회사** — ① 클라우드 · 내 서버에서 24시간 일하는 사무실 ② 휴대폰(웹 화면 · Slack)으로 보고받고 승인 · 지시 ③ 회사 하나의 맥락 · 지식 위에서 일할수록 나아지는 팀(자기 개선 순환).
- **방향 원칙(결정 86): 어려운 건 뒤에서 서비스가, 쉬운 건 앞에서 대표가** — 기억 · 지식 관리 · 24시간 운영 · 비용은 서비스가 풀고, 대표는 직관적인 보이는 화면만 만난다.

## 2. 대상 사용자
**혼자 또는 소수로 창업을 막 시작하는 사람 가운데, 컴퓨터 · 복잡한 소프트웨어에 익숙하지 않은 사람**(아이디어 · 준비 · 출시 직후 단계, 사업 종류 무관 — 결정 73 · 84). 1인 창업자, 프리랜서, 1인 크리에이터. 브랜드 신념: "AI를 누구나 사용할 수 있지만 아무나 사용할 수는 없습니다" — 그 간극을 잇는다(결정 84). **기본 경로는 설치 없이 쓰는 온라인판**, 직접 설치하려는 사람(파워유저 · 개발자 포함)에게는 설치를 도와준다. **소유자 1명의 사무실**이 기준이며 여러 사람이 함께 쓰는 사무실은 범위 밖이다. 기본 경로는 비기술 사용자 기준으로 단순하게, 실행 환경·AI 연결·직원별 설정은 고급 경로로 둔다(제안).

## 3. 핵심 가치와 지표
| 우선순위(제안) | 가치 | 관찰 지표 |
| --- | --- | --- |
| ① 핵심 | 맡겨두면 알아서 돌아감 | 주간 사이클당 사용자 개입 시간, 경미 수정 이하 채택률 |
| ② 동력 | 참여할수록 좋아지는 품질 | 같은 피드백 재발률, 회차별 수정량 |
| ③ 애착 | 내 회사를 키우는 재미 | 주간 재방문, 4주 유지 |
| ④ 기반 | 과정이 보임 | 복귀 요약만으로 상황 파악 가능 여부 |

성장은 실제 능력 향상(축적된 피드백·지식)에서만 계산하며 가짜 게임 수치를 만들지 않는다.
**대표가 들인 시간(결정 72):** 화면이 보이고 움직임이 있을 때만 영역별로 잰다 — 일한 시간(결정 · 확인 · 대화 · 관리, 줄어들수록 ①에 가까움) · 사무실에 머문 시간(③ 애착) · 준비 시간. 콘텐츠 지표 · 회사 화면 · 복귀 요약에서 회차별 · 주별로 본다.

**결정 77(2026-10-04): R1 오픈소스를 먼저 한다.** Hermes Agent처럼 한 줄 설치 · `agent-office` 명령 · 내 컴퓨터에서만 열리는 웹 화면, 라이선스 AGPL-3.0, 비공개 저장소에서 정리한 뒤 공개. 사용자가 자기 컴퓨터의 공식 Claude Code에 자기 구독으로 로그인하는 구조라 R1의 Claude 조건을 만족한다. 공개 전 할 일: [open-source](specs/open-source.md).

## 5. R0 대표 업무 — 창업 첫 달 (결정 73으로 개정)
**개정:** 업무는 사업에 맞춰 **업무 블록을 조합**한다. 첫 주 결과물은 **사업 진단 + 이번 달 실행 계획**(대표 확인), 이후 주간 회차에서 설계도의 블록(시장 조사 · 고객 인터뷰 · 가격 계산 · 준비 체크리스트 · 랜딩 문구 · 첫 고객 확보 계획 · 콘텐츠 운영 …)을 돌린다. 결과물 기본은 문서 · 표 · 체크리스트 저장과 대표 확인이다. 상세: [business-setup](specs/business-setup.md).

아래 '콘텐츠 운영'은 이제 **블록 하나**(콘텐츠가 필요한 사업에서 고르는 것)다 — 지금 구현된 흐름:
트렌드 조사 → 주간 기획 → 블로그 글·뉴스레터·SNS 짧은 글·이미지/썸네일 제작 → 검수 → 사용자 확인 → 게시.

| 산출물 | 종점 |
| --- | --- |
| 블로그 글 | Ghost, WordPress 게시 |
| SNS 짧은 글 | Threads, LinkedIn(개인 프로필) 게시 |
| 뉴스레터 | 최종 초안 저장(Notion/Docs), 발송은 범위 밖 |
| 이미지·썸네일 | 게시물에 첨부. 생성 경로 검증 순서: Codex 구독 → Gemini 구독 → 이미지 API 키 |
| 조사·기획 자료 | Notion / Google Docs 저장 |

**팀은 한 명씩 채용한다(결정 54).** 첫 직원은 사업 파트너 매니저이고, 매니저가 사업 기획 회의 후 다음 채용을 한 명씩 제안한다. 아래 4인은 로드맵 예시이지 기본값이 아니다.
로드맵 예시: 매니저(기획·검수) → 리서처 → 작가 → 디자이너. 다 채워졌을 때의 흐름: 리서처 → 매니저(기획) → 작가 → 디자이너 → 매니저(검수) → 사용자 확인 → 게시. 인원이 덜 찼을 때는 할 수 있는 일(예: 조사·기획만)과 다음 채용 후 가능한 일을 구분해 보여준다.
**직무 추가(결정 71):** 마케터(배포 계획 · 홍보 문구) · 편집자(블로그 교정 — 게시 확인은 교정본으로) · 영상 PD(숏폼 대본 · 스토리보드, 영상 파일은 만들지 않음) · SEO 담당(검색 키워드 브리프 → 기획). 매니저는 한 명, 다른 직무는 여러 명 둘 수 있고 같은 직무끼리 회차 업무를 돌아가며 나눠 맡는다.

## 6. 사용자 경험
상세: [experience.md](specs/experience.md)
1. **시작:** 사업 설명 → AI 연결(면접부터 AI가 일하므로 먼저 연결).
2. **첫 채용 = 매니저 면접(미니 사업 회의):** 후보 2–3명이 각자 사업 진단(방향·첫 한 달 계획·먼저 묻고 싶은 것)을 제시 → 선택 → 말투·성향·보고 스타일·외형·이름 조절 → 계약서로 고용(결정 54·55).
3. **사업 기획 회의:** 고용한 매니저가 자기 말투로 다음 행동에 필요한 질문만 하고(모르면 "조사해서 제안받기") 브리프를 정리한다.
4. **다음 채용:** 매니저가 역할·이유를 담은 채용 로드맵을 제안 → 후보 2명이 내 주제로 짧은 샘플(추정 사용량 표시) → 선택·조절 → 고용. 한 명씩 반복한다(결정 56).
5. **사무실(기본 화면):** 상단 요약 · 실적 자원 / 중앙 3D 공간 / 직원 상세 패널 / 활동 기록 / 결정·결과함. 빈 부지를 눌러 짓고, 배치 모드로 물건을 옮긴다. 목록 보기는 보조.
6. **확인:** 무엇을·어디에·언제를 보여주고 실행/수정/보류. 승인 후 실질 변경 시 재확인. 무응답은 승인으로 보지 않는다.
7. **복귀:** 텍스트 요약(새 결과, 필요한 결정, 멈춘 업무, 한도·재연결) + 선택형 하이라이트 리플레이(실제 이벤트, 시각 표시, 결정 우선).

## 8. 연결과 실행
- **앱:** Notion, Google Drive·Docs, Slack은 `설정 → 연결된 앱`에서 관리([integrations.md](specs/integrations.md)). 게시 플랫폼 4종도 같은 곳에 두고, 토큰 만료일과 예약 실행 가능 여부를 표시한다.
- **게시 조건:** Threads·LinkedIn은 API 예약이 없으므로 Agent Office 스케줄러가 예약을 소유한다(VPS 필요). Threads 이미지는 공개 URL이 필요하다. LinkedIn은 60일마다 재인증이 필요하다([publishing.md](specs/publishing.md)).
- **AI:** 사용자 구독 연결. **구독 한도가 곧 예산**이다. 한도에 도달하거나 연결이 만료되면 해당 업무만 멈추고, 자동 전환이나 추가 과금은 없다. 리셋 시각 표시와 자동 재개, 직원별 사용 점유율을 '급여'처럼 표시(제안). 상세: [ai-connections.md](specs/ai-connections.md)
- **실행 환경:** 사무실 단위로 하나의 책임 실행 환경을 둔다. 로컬은 기기 상태에 의존한다. VPS에서는 화면을 닫아도 계속 실행된다. 연결이 끊기면 마지막 확인 시각을 표시하고 가짜 실시간을 보여주지 않는다([deployment.md](specs/deployment.md)).

## 9. 사무실 표현과 공간
상세: [domain-motion.md](specs/domain-motion.md) · [growth-office.md](specs/growth-office.md) · [space-generation.md](specs/space-generation.md) · [characters.md](specs/characters.md)
- **3D**(결정 63). WebGL이 없으면 2D로 대체한다.
- **공간은 도메인에 맞춰 생성한다(결정 67, '필요의 방').** 매니저(AI)가 회사 설명 · 팀을 보고 공간 설계도를 쓰고 엔진이 짓는다 — 사무실이 아니어도 된다(스튜디오 · 연구소 …). 회차 보드 · 결재함 · AI 연결 · 회사 지식 · 마일스톤 · 간판은 어느 공간에나 있고 모습만 바뀐다. 설계도가 없을 때는 단계 레이아웃(공유 오피스 한 칸 … 사옥)을 쓴다.
- **짓기(결정 68):** 사무실 레벨(=성)이 지을 수 있는 방 수를 정하고, 안 지은 방 · 자리 · 꾸미기는 빈 부지(점선 칸)로 보인다. 직무별 실적 자원(실제로 끝낸 일에서만 쌓임)을 써서 짓는다. AI 사용량은 따로 보여 준다.
- **배치:** 배치 모드(또는 물건을 꾹 누르기)로 끌어서 옮기고 돌린다. 방 밖 · 겹침 · 문 앞은 놓을 수 없다.
- **새 방 요청(결정 69):** 설계도에 없는 방을 글로 요청하면 매니저(AI)가 설계한다. 설계하는 동안이 공사 기간(가림막), 끝나면 건물 오른쪽 별관에 지어진 채로 생긴다(있던 방은 움직이지 않음).
- **기능 시설 업그레이드(결정 70):** 시설 레벨이 오르면 그 화면에 편의 기능이 열린다(회차 결과물 내려받기 · 골라서 승인 · AI 사용 기록표 · 지식 내보내기/점검 · 기록 카드 저장). 핵심 기능은 잠그지 않는다.
- **연출:** 사무실 레벨 업(짐 상자 · 배너) · 승급(금빛 기둥) · 복귀 요약 하이라이트를 3D 사무실에서 다시 보기 · 직원 초상 3D — 모두 실제 기록이 바뀐 순간에만.
- **캐릭터:** 키우는 재미가 있는 AI다운 존재, 신화 속 전령 세계관(결정 64) — 컨셉 재기획 예정, 지금은 전령 초안을 임시로 쓴다.
- **모션은 활동 이벤트 기록에서만 파생된다.** 이벤트 없는 장면을 만들지 않고, 텍스트 상태가 항상 우선한다.
- 인계·검토 요청은 걸어가서 전달하고(물건을 피하는 길 찾기, 층이 다르면 엘리베이터), 직원 간 DM은 자리에서 말풍선(묶음 개수)으로 표현한다.
- 직원별 연출 대기열과 최소 표시 시간을 둔다. 밀리면 최신 상태로 건너뛴다. 동작 줄이기와 목록 보기에서도 같은 정보를 제공한다.

## 10. 성장·학습·지식
- **성장 요소:** 직원 성장(배운 것·숙련도), 회사 성과 기록, 직원 개성·관계, **공간 성장**(사무실 레벨 업 · 짓기 · 새 방 · 시설 업그레이드 — 결정 66–70). 모든 성장 수치는 실제 기록에서만 나온다.
- **피드백 입력:** 인라인 코멘트, 평가 버튼+이유, 직원 DM, 외부 수정 자동 감지.
- **반영:** 자동으로 적용하고 직원 카드의 `배운 것`에 출처와 함께 표시하며, 수정·삭제할 수 있다. 외부 수정에서 나온 규칙은 `추정`으로 표시(제안).
- **지식:** 회사 공통 원칙과 검토된 교훈은 공유하고, 원본 자료·대화는 프로젝트 단위로 둔다. 승격에는 사용자 확인이 필요하다([knowledge.md](specs/knowledge.md)).

## 11. 범위
**R0 포함:** 위 5–10 전부 — 업무는 사업 맞춤 블록 조합(결정 73), 플랫폼 게시는 콘텐츠 운영 블록을 쓸 때만. 로컬↔VPS 전환, 직원별 AI 연결 지정, 회사 지식 승격 포함.
**R0 제외:** 여러 TF 동시 운영, 그룹(계열사) 단계. 여러 사람이 쓰는 사무실, 관리형 서버, 서비스 제공 AI, Instagram, X, 뉴스레터 발송, LinkedIn 회사 페이지, 직원별 범용 컴퓨터 조작. (사무실 공간 확장은 결정 66으로 포함으로 바뀜)

## 12. R0 완료 기준 — 기능 완성 판정
> 개정 예정(결정 73): 3번은 "사업 설계도 → 첫 주 사업 진단 · 실행 계획 확인 → 설계도의 업무 블록으로 한 주가 돌고 결과물이 저장된다(콘텐츠 운영 블록을 고르면 승인된 버전으로만 게시)"로 바꾼다. 확정은 P4에서.
1. 빈 상태에서 사업 설명 → 질문·브리프 → 팀 제안·수정 → 고용까지 진행할 수 있다.
2. 직원 간 인계가 수락 기반으로 기록되고, 대화·업무·모션에서 같은 인계를 확인할 수 있다.
3. 한 주 사이클이 Notion/Docs 저장과 4개 플랫폼 게시까지 완료되며, 게시는 승인된 버전으로만 실행된다.
4. 결과가 불명확한 게시를 다시 실행하지 않고 "확인 필요"로 표시한다. 대기·실패를 완료처럼 보이지 않는다.
5. VPS에서 화면을 닫은 채 예약된 한 주 사이클이 완료되고, 복귀 요약과 리플레이로 확인할 수 있다.
6. 한도 도달, 토큰 만료, 연결 해제가 해당 업무에만 정확히 반영되고 자동 과금·전환이 없다.
7. 피드백이 `배운 것`으로 보이고, 다음 회차 결과물에 반영된다.
