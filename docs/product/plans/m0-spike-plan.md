# Agent Office — M0 기술 스파이크 계획

작성일: 2026-10-02
상태: 스파이크 스택(TypeScript/Node)과 게시 테스트 보류는 사용자 확정(결정 58·59). 스파이크 목록·순서·통과 기준·일정은 기획 제안.
> 2026-10-02 갱신: 첫 AI 연결을 Claude 구독(Claude Code CLI)으로 먼저 구현했다(결정 61). A의 질문(로그인, 무인 실행, 병렬, 웹 조사, 한도, 사용량, 성향 반영, 중단·재개)을 Claude CLI에 먼저 적용하고 Codex는 같은 표로 뒤이어 확인한다. Claude CLI는 한도 %를 알려주지 않으므로 A5는 "표시하지 않음"으로 정해져 있다. 로컬 기본 시스템이 있으므로 스파이크는 `spikes/` 대신 실제 연결 코드(`src/ai`)로 확인한다.

상위 계획: [r0-plan.md](r0-plan.md) · 근거: [ai-connections.md](../specs/ai-connections.md), [publishing.md](../specs/publishing.md), [integrations.md](../specs/integrations.md)

## 1. 목적
제품 코드를 쓰기 전에 R0 전제가 실제로 성립하는지 확인한다. 산출물은 코드가 아니라 경로별 **가능 / 조건부 / 불가 / 보류** 판정과 그 근거, 그리고 대안이다.
스파이크 코드는 `spikes/`에 두는 버리는 코드다. 제품 코드로 옮기지 않고 배운 점만 옮긴다.

## 2. 원칙
- 공식 문서에 있는 공식 경로만 쓴다. 다른 앱의 쿠키·세션·토큰을 추출하지 않는다.
- 비밀정보(구독 로그인, API 키, OAuth 토큰)는 사용자가 직접 발급하고 `.env.local`에 입력한다. git과 로그에 남기지 않는다.
- 외부에 공개되는 행동(SNS·블로그 게시)은 하지 않는다. 게시 테스트는 보류한다(결정 59).
- 결과에는 날짜와 버전을 적는다. 확인하지 못한 것을 "가능"으로 쓰지 않는다.
- 한도를 일부러 소진시키지 않는다. 한도 도달 동작은 문서·오류 코드로 확인하고, 자연히 발생하면 기록한다.

## 3. 스파이크 — 위험이 큰 순서
### A. Codex 구독으로 직원 실행 (3일) — R0 전제의 핵심
| # | 확인할 질문 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| A1 | 구독 로그인이 로컬과 화면 없는 서버에서 모두 되는가 | 로컬은 브라우저 로그인, 서버는 디바이스 코드 로그인. 프로세스 재시작 후 유지 확인 | 둘 다 로그인되고 재시작 후에도 유지됨 |
| A2 | 사람 개입 없이 업무 한 개를 끝까지 실행할 수 있는가 | Codex SDK/app-server로 역할 지시 + 브리프 → 정해진 JSON 형식의 결과 | 10회 중 9회 이상 형식에 맞는 결과. 실패 형태를 수집함 |
| A3 | 여러 직원이 한 구독으로 동시에 일할 수 있는가 | 직원 2–3명 병렬 실행 | 병렬 가능 여부 판정. 불가면 직렬 큐 필요를 기록 |
| A4 | 리서처가 웹 조사를 할 수 있는가 | 비대화형 실행에서 웹 검색·페이지 읽기 사용 | 출처 URL이 붙은 조사 요약 생성. 불가면 대안 기록 |
| A5 | 사용 한도를 읽을 수 있는가 | 로그인 상태·사용 한도 조회 응답의 필드(비율, 재설정 시각), 갱신 주기 확인 | 화면에 "이번 주 n% 사용 · 재설정 시각"을 실제 값으로 표시 가능 |
| A6 | 업무마다 한도를 얼마나 쓰는가 | 업무 전후 한도 비교: 면접 진단 3명, 후보 샘플 2명, 조사 요약, 블로그 초안 1편, SNS 6편 | 업무별 추정치 표. UI "추정 사용량"과 주간 회차 예산의 근거가 됨 |
| A7 | 한도 도달·인증 만료·일시 오류를 구별할 수 있는가 | 문서와 오류 응답 형태 확인. 만료는 로그아웃으로 재현 | 세 경우를 다른 업무 상태(한도 대기 / 재연결 필요 / 재시도)로 매핑 가능 |
| A8 | 성향·말투 설정이 결과에 실제로 반영되는가 | 같은 브리프에 성향 설정 3종 → 결과를 섞어 설정을 맞히기. 말투는 5턴 대화에서 유지 확인 | 3개 중 2개 이상 맞힘, 말투 5턴 유지 |
| A9 | 실행 중인 업무를 멈추고 다시 시작할 수 있는가 | 실행 중 취소, 프로세스 종료 후 재개 | 중복 실행 없이 "중단됨/재개됨"으로 기록 |

### B. 이미지 생성 (1.5일) — 검증 순서: Codex 구독 → Gemini 구독 → 이미지 API 키
| # | 확인할 질문 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| B1 | Codex 구독으로 비대화형 이미지 생성이 되는가 | SDK/app-server 경로에서 생성 시도(공식 문서 미확인 항목). 한도 소모량 측정 | 생성 성공 + 장당 한도 % 기록, 또는 "불가" 근거 |
| B2 | Gemini 구독에 공식 프로그램 경로가 있는가 | 공식 문서 확인 후 경로가 있으면 시험 | 경로 유무 판정 |
| B3 | 이미지 API 키 경로(기준선) | 블로그 썸네일 1200×630, SNS 정사각 1080×1080 생성 | 두 규격 생성·저장, 장당 비용 기록 |

통과: 최소 한 경로로 두 규격이 생성된다. API 키 경로는 사용자가 비용 상한을 정한 뒤에만 사용한다.

### E. 결과물 저장과 알림 — Notion · Google Docs · Slack (1.5일)
| # | 확인할 질문 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| E1 | Notion에 결과물을 저장할 수 있는가 | 지정 페이지 아래 페이지 생성. 마크다운 → 블록(제목·목록·링크·이미지). R0에 내부 통합으로 충분한지 확인 | 서식이 유지된 페이지 + 링크 회수 |
| E2 | Google Docs에 최소 권한으로 저장할 수 있는가 | `drive.file` 범위로 지정 폴더에 문서 생성·서식. 로컬(설치형)과 서버(웹) 인증 흐름 비교 | 문서 생성 + 링크 회수, 서버에서 토큰 유지 |
| E3 | Slack 알림을 보낼 수 있는가 | 내 워크스페이스의 알림 채널에 `chat.write`로 결정 요청 알림 + 앱 딥링크 | 알림 수신, 링크로 앱 결정함 진입 |
| E4 | 다시 실행할 때 중복 생성을 막을 수 있는가 | 같은 결과물 버전을 두 번 저장 시도 | 중복 방지 키로 두 번째 생성 차단 또는 기존 문서 갱신 |

### F. 상시 실행 — 본인 VPS (1.5일)
| # | 확인할 질문 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| F1 | 화면 없이 서버에서 업무가 도는가 | VPS에 Node 런타임 + Codex 디바이스 로그인 → 업무 1개 실행 | 브라우저를 닫은 상태로 완료, 기록 남음 |
| F2 | 예약 실행이 재시작을 견디는가 | 저장소 기반 작업 큐로 정해진 시각에 실행. 실행 직전 프로세스 재시작 | 놓친 예약을 한 번만 실행(중복 없음) |
| F3 | OAuth 콜백을 받을 수 있는가 | 도메인 + TLS로 콜백 수신(Notion·Google, 이후 LinkedIn·Threads 공통 전제) | HTTPS 콜백으로 토큰 발급 |

Claude 구독 경로는 Anthropic 문의 회신 전에는 시험하지 않는다(결정 34).

### 보류 — C. 게시 · D. 이미지 공개 호스팅 (결정 59)
사용자 결정으로 이번 M0에서는 시험하지 않는다. **M2(게시) 착수 전에 반드시 수행한다.** 그때 확인할 항목:
- Ghost·WordPress: 초안 생성, 예약(`scheduled` / `future`), 미디어 업로드, 결과 URL 회수. 테스트 대상은 그때 정한다.
- Threads: 테스터 등록, 이미지 컨테이너 생성 → 게시, 장기 토큰 갱신, 공개 URL 이미지 요구 조건.
- LinkedIn: 3-legged OAuth, 이미지 업로드 → 게시, 60일 재인가 흐름. API 버전 202510은 2026-10-15 종료이므로 그때의 최신 버전으로 시험한다.
- 공통: 결과가 불명확할 때 플랫폼에서 게시 여부를 확인하는 방법(최근 게시물 조회 등).
- D: 승인된 이미지만 게시 직전에 공개 URL로 노출하는 방식. Threads 게시와 함께 시험한다.

## 4. 결과에 따른 판단
| 결과 | 다음 행동 |
| --- | --- |
| A1 또는 A2 불가 | 즉시 멈추고 R0의 AI 경로를 다시 결정한다(예: API 키 우선). 사용자 결정 필요 |
| A3 병렬 불가 | 직원 업무를 직렬 큐로 실행한다. 사무실 모션에 "순서 대기"를 반영한다 |
| A4 불가 | 검색 API 키를 추가하거나, 사용자가 준 자료 중심으로 조사한다. 사용자 결정 필요 |
| A5 불가 | "이번 주 n%"를 표시하지 않는다. 한도 도달 사실만 표시하고, 추정치는 `추정`으로 표시 |
| A6에서 주간 회차가 한도를 많이 씀 | 기본 분량(블로그 1 + SNS 6)을 줄이거나 회차 안에서 사용량을 나눠 배치한다 |
| A8 구별 불가 | 성향을 실제 동작 규칙(확인 질문 빈도, 보고 길이, 초안 개수 등) 중심으로 다시 정의한다. 반영되지 않는 슬라이더는 두지 않는다(결정 55) |
| B1·B2 불가 | 이미지 API 키를 쓴다. 사용자의 비용 상한을 확인하고 장당 비용을 표시한다 |
| F2 불안정 | 별도 작업 큐 도입을 검토한다 |

계정 생성, 로그인, 키 발급은 사용자가 직접 한다. 스파이크 코드는 비밀정보를 화면에 출력하지 않는다.

- [ ] (B3용) 이미지 API 키와 사용 상한 금액
- [ ] VPS 1대 + 도메인(HTTPS) — F
- [ ] Notion 워크스페이스와 테스트 페이지 — E1
- [ ] Google Cloud 프로젝트(OAuth 동의 화면 테스트 모드)와 테스트 폴더 — E2
- [ ] Slack 워크스페이스와 알림 채널 — E3

## 6. 작업 구조와 산출물
- 런타임: Node LTS + TypeScript(결정 58). 스파이크별 폴더로 나누고 공통 설정만 공유한다.
  ```
  spikes/
    a-codex/     로그인, 비대화형 실행, 병렬, 웹 조사, 한도, 사용량 측정, 스타일 반영
    b-image/     codex, gemini, api-key
    e-storage/   notion, gdocs, slack
    f-vps/       서버 실행, 예약 큐, https 콜백
  ```
- 결과 기록: `docs/product/plans/m0-results.md`. 스파이크마다 카드 한 장을 쓴다.
  - 질문 / 판정(가능·조건부·불가·보류) / 근거(날짜·버전·로그 요약) / 측정값 / 제품에 주는 영향(바뀌는 결정·화면) / 대안
- 결과를 반영할 문서: ai-connections.md(실제 지원 범위), publishing.md §4(미확인 항목), r0-plan.md(M1–M2 범위), UI의 추정 사용량 수치(S3 면접·샘플, S7 전력실).
